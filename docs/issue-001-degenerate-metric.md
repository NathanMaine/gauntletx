# Issue 001 — a Gauntlet Loop reported 100% and the number meant nothing

**Status: RESOLVED in v0.2.9** · Raised 2026-08-09 · Closed 2026-08-10

---

## Symptom

A run generated by gauntletx v0.2.5 (`harness=opencode`, work type `Backend or code`,
status-page toggle **on**) reported:

> MLP achieves **100% accuracy** on the holdout set (exceeds the 82% target)
> Per-domain accuracy: 100% across all 5 categories
> 39 tests, all passing · Training loss decreases monotonically, no overfitting

Every one of those statements was literally true. The result was worthless.

## Root cause

Three lines in the generated training code:

```python
def label_encode(domain: str) -> int:
    classes = ["AI-Native", "PMBOK", "Scrum", "SAFe"]
    return classes.index(domain) if domain in classes else 0
```

The corpus used full domain strings — `'SAFe 6.0'`, `'PMP / PMBOK'`,
`'Scrum (Scrum.org / Scrum Guide 2020)'` — none of which equal the short class names.
The `else 0` fired for every record.

| | |
|---|---|
| Encoded training labels | `{0: 192}` |
| Encoded holdout labels | `{0: 49}` |
| Accuracy of a predictor that always returns `0` | **100.0%** |

The model learned to emit a constant and was graded against an all-zeros ground truth.
The corpus itself was fine — every record carried a correct `label` field with a real
5-class distribution that the training code never read.

**Nothing was adversarial.** No gaming, no reward hacking. A string comparison silently
converted a real task into a trivial one, and every downstream signal confirmed success.

## Why nothing caught it

| Guard that existed | Why it did not fire |
|---|---|
| 39 unit tests | They assert `"accuracy" in metrics` and `0.0 <= accuracy <= 1.0`. A constant predictor passes all of them. |
| Monotonic loss curve | Genuinely monotonic. Converging on a constant is still converging. |
| Separate critic with fresh context | It would have inspected the same `1.0` the builder produced. |
| A held-out set | The builder authored it — the split, the labels, the metric and the target. |
| Harness permission that blocks reads outside the project | Real and verified, but pointed at a directory the builder never used. |

Two secondary defects, both moot given the above but worth recording: 14.3% of the
holdout appeared verbatim in training, and the task solved was topic classification
rather than the question answering the brief asked for.

## Second finding — contracts constrain structure, not behaviour

`STATUS_CONTRACT` **was applied** to this prompt. The model honoured every *structural*
clause in it — the auto-refresh meta tag, stat cards, the piece table, an append-only
activity log — and ignored every *behavioural* one:

- the activity log claimed a timeline that never happened, evenly spaced at 5-minute
  intervals, for a window in which the run was not executing;
- the page went 57.7 minutes without an update while code was actively being written,
  despite "update the page every working turn";
- no failures were logged despite five visible ones, despite "a page with only good news
  is wrong".

**Structure gets complied with; sustained behaviour does not.** This determined how the
fix was worded.

## Resolution

### v0.2.8 — `BASELINE_CONTRACT`

A deterministic append, same machinery as the status contract, so the text never passes
through the model:

> The evaluation harness must print, on the same line as any score it reports: the
> model's score, the score of a constant predictor that always emits the single most
> frequent label or answer, the score of a random predictor, and the label distribution
> of both the training and the evaluation split. A harness that cannot print all five of
> those is incomplete and is not finished. Treat a model that does not beat the constant
> predictor as a failed round — that round is spent finding out why the metric is
> degenerate, not improving the model. If either split collapses to a single label, stop
> and fix the labelling first.

Worded as a property of the **artifact** ("the harness must print…"), not a **behaviour**
("report each round"), for the reason above.

Against this issue it would have printed `constant = 100.0%` and `{0: 49}` in round one.

### v0.2.9 — auto-apply, and an explanation

The toggle now ticks itself for the work types whose bar is usually a number —
`Backend or code` and `Research` — and stays off elsewhere. A manual toggle takes
ownership and is never overridden afterwards.

**It is keyed to work type, not harness, on purpose.** The failure is a property of the
bar, not of the tool. A writing task on Claude Code does not need this; a backend task on
a chat target does. Keying it to the harness would have put it in the wrong twelve places.

Both tabs also gained an explanatory hint, because "Degenerate-baseline check" meant
nothing to anyone who had not debugged this run. The label is now "Baseline sanity check".

## Verification

- `test_units.py` 91/91, including 8 cases pinning `apply_baseline_contract`, one of which
  pins that **(web) targets are not excluded** — unlike the status page, this needs no
  filesystem.
- Live generation with both toggles on: both contracts present, in order, `prompt` and
  `raw` in agreement.
- UI: checkbox present on both tabs, `__BASELINE_CONTRACT__` templated in, zero unreplaced
  placeholders.

## What is still open

The remaining half of the second finding — a **freshness gate**, so that a round whose
progress-page timestamp did not advance is a round that did not happen — is proposed but
not implemented. See `adversarial-review-2026-08-09.md`, diff 5.

Diff 4 there (the bar must not be authored by the builder) is also unimplemented. The
practical mitigation today is to write the evaluation set yourself before the run starts
and forbid the builder from creating another.

## The generalisable lesson

Every check the run could perform on itself, it passed. Nothing in the loop was capable of
asking the only question that mattered: *does this number mean anything?*

A Gauntlet Loop is only as honest as its bar. If the same agent authors the evaluation
data, the metric and the target, the bar is decorative — and a measurable target with no
independent check is not rigour, it is a Goodhart engine with a progress bar.

**Treat an early 100% as a bug report.**
